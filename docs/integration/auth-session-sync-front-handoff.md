# front / front2 인증 브로드캐스트 Handoff

## 목적과 탭별 동작

한 탭에서 로그인·로그아웃하면, 같은 브라우저에서 열려 있는 다른 탭도 새 인증 상태에 맞는
화면을 열도록 한다. front와 front2는 아래 채널과 메시지 규칙을 공유한다.

직접 로그인·로그아웃한 탭을 **송신 탭**, 알림을 받은 다른 탭을 **수신 탭**이라고 부른다.

| 상황             | 직접 실행한 탭 (송신 탭)                              | 알림을 받은 다른 탭 (수신 탭) |
| ---------------- | ----------------------------------------------------- | ----------------------------- |
| 로그인 최종 성공 | `LOGIN`을 보내고 기존 로그인 성공 코드가 이동 처리    | `router.push("/home")`        |
| 로그아웃 성공    | `LOGOUT`을 보내고 기존 로그아웃 성공 코드가 이동 처리 | `router.push("/login")`       |

예를 들어 A 탭이 `/login?returnTo=%2Frag`에서 로그인에 성공하면 `LOGIN`을 보낸 뒤
기존 로그인 코드에 따라 `/rag`로 이동한다. 알림을 받은 B 탭은 `/home`으로 이동한다.
송신 탭의 필수 비밀번호 변경, `returnTo`, 역할별 이동 순서는 기존 코드를 따른다.

## 공통 규약

채널 이름은 `civic-ai:auth:v1`이며, 전송 값은 대문자 문자열 `LOGIN` 또는 `LOGOUT`이다.
두 앱은 `BroadcastChannel`로 이 값을 주고받는다.

### 송신

아래 API의 성공 응답을 받은 다음, 송신 탭의 기존 화면 이동 전에 메시지를 보낸다.

| 메시지   | 송신 시점                                                                                |
| -------- | ---------------------------------------------------------------------------------------- |
| `LOGIN`  | 로그인 최종 성공. 2FA 사용 시 최종 인증까지 완료한 뒤 송신                               |
| `LOGOUT` | 로그아웃, 비밀번호 변경/재설정, 2FA 해제, 계정 비활성화에서 세션 무효화가 성공한 뒤 송신 |

송신 코드는 위 성공 처리에만 연결한다. 채널 생성·송신 오류는 `try/catch`로 처리하고
기존 인증 성공 흐름을 이어간다.

### 수신

로그인·공개 화면을 포함한 앱 루트에서 수신기를 한 번 등록한다. 수신 콜백은 메시지에 따라
앱의 일반 화면 이동 방식인 `router.push()`를 호출한다.

- `LOGIN` → `router.push("/home")`
- `LOGOUT` → 사용자 조회 캐시 정리 후 `router.push("/login")`

인증과 권한 확인은 기존 페이지/API 로직이 담당하며, 수신 탭의 목적지는 위 두 경로로
통일한다. 로그아웃 후 다시 로그인하면 `/login`을 거쳐 `/home`으로 이동한다.

아래 코드는 송수신 흐름의 예시다. `router`는 앱에서 사용하는 라우터다.

```ts
const channel = new BroadcastChannel("civic-ai:auth:v1");
channel.onmessage = ({ data }) => {
  if (data === "LOGIN") router.push("/home");
  if (data === "LOGOUT") {
    clearUserQueryCache();
    router.push("/login");
  }
};
// 로그인 API의 최종 성공 응답을 처리한 뒤:
channel.postMessage("LOGIN");
```

실제 앱에서는 위 오류 처리와 함께, 마지막 구독 해제 시 채널을 닫도록 구성한다.
`clearUserQueryCache()`는 각 앱의 사용자 조회 캐시를 비우는 함수를 뜻한다.

## front2의 송신·수신과 데이터 정리

front2는 [auth-session-events.ts](../../apps/web/lib/auth/auth-session-events.ts)에서 채널 하나를
공유한다.

| 함수                            | 역할                                           |
| ------------------------------- | ---------------------------------------------- |
| `sendAuthMessage(message)`      | 다른 탭에 `LOGIN` 또는 `LOGOUT` 전송           |
| `observeAuthMessages(callback)` | BroadcastChannel에서 받은 메시지를 콜백에 전달 |

송신 탭은 기존 인증 성공 처리에서 필요한 데이터를 정리하고 메시지를 보낸 뒤 이동한다.
수신 탭은 [AuthSessionSync](../../apps/web/components/auth/auth-session-sync.tsx)에서
메시지를 받아 필요한 데이터를 정리하고 고정 목적지로 이동한다.

로그아웃 성공 처리와 `LOGOUT` 수신 처리에서는 화면 이동 전에 React Query 캐시를 비운다.
front2는 `clearAppQueryCache()`로 현재 QueryClient의 조회·변경 캐시를 정리한다.
이후 로그인한 계정의 역할과 필수 설문 완료 여부는 새로 조회한다. 비밀번호 변경·재설정,
2FA 해제, 계정 비활성화처럼 세션을 끝내는 성공 처리에도 같은 규칙을 적용한다.

데이터 정리는 각 앱의 기존 함수를 재사용한다. RAG 대화 복원·계정 확인과 front의 Chat 연결
정리는 해당 기능의 코드에서 관리한다.

front에서는 위 송수신 규약에 맞춰 앱 구조에 적합한 함수명과 구독 방식을 선택하면 된다.

## 적용 범위와 앱별 처리

- 같은 브라우저 프로필·세션에서 scheme·host·port가 같은 origin의 탭끼리 통신한다.
  로컬에서 두 앱을 함께 검증할 때는 하나의 프록시 origin으로 접속한다.
- BroadcastChannel 지원 환경에서 구독 중인 탭에 알림을 실시간으로 전달한다.
  새로 열거나 신호를 놓친 탭의 인증 확인은 앱의 진입·복귀 처리에서 다룬다.
- `push`는 방문 기록을 추가한다. 이전 기록으로 돌아갈 때의 화면·캐시 복원은
  각 앱에서 처리한다. 로그아웃 시 사용자 캐시·대화·임시 입력을 정리한다.
  front의 Chat은 연결/재접속·전송 대기열·대화 캐시를 현재 계정 기준으로 정리해야 한다.
- 여러 탭에서 인증을 동시에 바꾸는 경우에도, 최종 접근 권한은 API가 현재 쿠키를 기준으로 판단한다.

## front 구현 후 확인할 동작

실제 두 앱의 탭에서 다음 동작을 확인한다.

- 양방향 송수신과 로그인·로그아웃·계정 전환 시 수신 탭의 고정 목적지 이동
- `returnTo`가 있는 수신 탭도 로그인 알림을 받으면 `/home`으로 이동
- 로그인·2FA가 최종 성공했을 때만 `LOGIN` 송신
- 계정 전환 및 뒤로가기 시 Chat 데이터와 연결을 현재 계정 기준으로 정리
