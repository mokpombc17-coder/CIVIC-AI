# RAG 계정 전환과 이전 대화 노출 방지

이 변경은 `LOGIN`/`LOGOUT` 브로드캐스트 커밋과 분리한다.
[공통 신호 규약](../integration/auth-session-sync-front-handoff.md)은 그대로 유지하며,
신호 수신 후 이동 전에 `/me`를 추가 호출하지 않는다.

## 문제와 기존 방어

기존 RAG sessionStorage 스냅샷·초안에는 `ownerUserId`가 있고, 다른 사용자 ID로 읽으면 삭제한다.
그러나 이전 페이지의 서버 props와 React state가 함께 복원되면 그 ID 자체가 과거 계정일 수 있다.
저장소 소유자 비교만으로는 해당 화면이 현재 쿠키의 사용자와 같은지 알 수 없다.

## 처리

- 기존 인증 성공 처리와 `AuthSessionSync`의 메시지 수신 처리에서
  공통 `clearAuthSessionData()`를 호출한다. 이 함수가 `clearRagConversationSnapshot()`을
  사용해 대화 스냅샷과 초안을 삭제한다. RAG 밖에서 받은 메시지도 이동 전에 처리한다.
- 참여자 RAG 화면은 서버가 전달한 사용자 ID를 key로 하는 `RagSessionBoundary` 안에서 렌더링한다.
  최초 `/me` 확인 전에는 대화 컴포넌트를 마운트하지 않아 스냅샷을 노출하거나 이전 작업을 재개하지 않는다.
- 탭 복귀/focus 때도 `/me`의 현재 사용자 ID·ACTIVE 상태를 확인한다. 확인 중에는 기존 대화와
  입력을 숨기고, 같은 계정이 확인되면 그대로 다시 보여준다. 메시지를 놓친 경우도 이 경계에서 확인한다.
- 계정이 달라졌거나 비활성화되면 스냅샷을 지우고 `/home`으로 문서를 교체한다.
- `/me` 401은 기존 `/auth/refresh?returnTo=...` 흐름에 맡긴다. 네트워크 오류·429·5xx·잘못된
  응답은 로그아웃으로 판단하지 않고 내용을 숨긴 채 재시도 UI를 보여준다.
- `RagSessionBoundary`도 같은 수신 구독을 사용해 메시지를 받으면 현재 대화를 숨기고
  언마운트해 질문 요청/스트림을 중단한다. 진행 중이던 계정 확인 결과는 무시한다.
  이동은 `AuthSessionSync`가 담당하며, 현재 탭에서 직접 실행한 인증 동작은 기존 이동을 따른다.
- `pagehide`에서 대화를 동기적으로 숨긴다. `pageshow.persisted`에서는 숨김을 유지한 채 전체
  문서를 새로 로드해 최신 서버 props와 계정 확인을 거친다. 방문 기록을 지우는 방식은 아니다.
- 공통 `authenticatedFetch`는 요청이 중단되었거나 송신·수신 과정에서 인증 변경을 관찰했다면 401 후
  갱신/재전송을 진행하지 않는다. A가 시작한 질문을 B의 쿠키로 자동 재전송하는 일을 줄인다.
  신호를 놓친 모든 요청을 원자적으로 막는 기능은 아니며 API의 세션/작업 소유권 검사는 여전히 필수다.

## 검증

코드 검증은 `pnpm check`로 실행한다.

브라우저에서는 실제 front2와 로컬 Auth 응답 대역, 사용자별 합성 RAG 스냅샷으로 검증했다.
동일 계정 복원, 계정 전환 시 삭제, 다른 계정 스냅샷 거부, 목적지 로딩 중 로그아웃 화면 숨김,
BroadcastChannel 없이 실제 창 focus 복귀, 일시 오류 후 초안 유지, 실제 뒤로가기를 확인했다.
`pagehide`/`pageshow.persisted`는 별도 합성 lifecycle 이벤트로도 검사했다. 이 검사를 실제
브라우저의 bfcache 채택 보장이나 운영 RAG 모델 응답 검증으로 해석하지 않는다.

추가로 실제 로컬 Main/Auth와 production build를 Chrome 세 탭에서 검증했다. 직접 로그인한
탭의 `/mypage` 복귀, 수신 탭의 `/home` 이동, 로그아웃 수신 탭의 `/login` 이동, 다른 계정으로
로그인한 뒤 RAG 뒤로가기에서 이전 대화가 표시되지 않는 것을 확인했다. 이 검사도 RAG 답변은
사용자 ID를 연결한 합성 스냅샷을 사용하며, 실제 질의 생성이나 모델 호출은 포함하지 않는다.

front의 Chat은 자체 연결·전송 대기열·캐시 구조에 맞는 별도 처리가 필요하다.
RAG 경계를 그대로 복사하기보다는 사용자 확인 전 복원 금지와 이전 계정 작업 중단 원칙을 적용한다.
